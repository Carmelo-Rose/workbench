# 商品套图 vs「服装视觉生产线」：现状对照与差距

> 背景：外部有一份按**女装**写的「服装视觉内容生产线」六层拆解（商品保真 / 数字模特 / 视觉导演 / 资产库 / 生产引擎 / 质检闭环）。
> 本文把它逐层对到我们已有的商品套图（`product_pipeline`）上，说明哪些已经有了、哪些是缺口、以及缺口的优先级。
>
> 结论：**骨架属于同一类系统，我们是其中第 1、3、5 层的一个具体实现，覆盖面约三分之一，且品类不同（帽子 ≠ 女装）。**

---

## 1. 逐层对照

### 层 1 · 商品保真

**已有：**

- 抠图（走网关，GPU 执行）
- 像素级颜色分组、白底判定、裁切框 —— `src/lib/mono/product-classify.ts`
- `x_` 前缀细节特写分流：不抠图、不参与颜色识别，直接进 11 号细节页 —— `product-pipeline.ts` `partitionSources`
- 模板里的 `productLock` 保真契约（商品是唯一权威，不得改颜色/形状/结构）

**缺口：**

- 技术路线是「商品参考图 + gpt-image-2 多图参考生成」，不是 ControlNet / IP-Adapter / 虚拟试衣 / 局部重绘
- `buildModelPrompt()`（`src/lib/mono/product-template.ts:85`）**当前是实验态**：只返回 `look.text + CAMERA_STYLE`，保真/构图/禁止项三段被注释保留。也就是说保真层在提示词侧现在是关着的，正在评估出图效果

---

### 层 2 · 数字模特

**已有：** 基本没有。

`template.json` 的 `looks`（A/B/C）只是一段自然语言人物描述，按颜色序位选用（colourway 0 → look A）。没有身份 LoRA、没有人脸参考图、没有一致性约束。

**后果：** 同一个任务的 7 张模特图之间，模特不是同一个人；跨批次更不是。

**这是与那份方案差距最大的一层，也是它整篇最强调的东西。**

---

### 层 3 · 视觉导演（镜头 Skill）

**已有 —— 形态几乎一致。**

`template.json` 的 `modelSlots` 就是它说的 skill：每个槽位一段 `framing`，写明景别、姿势、视线方向、头部角度。`product-template.ts` 顶部的 `CAMERA_STYLE` 是全局镜头语言（哈苏 X2D 100C / 80mm f2.8 / 原生色彩配置文件）。

**差别：** 我们是「每品类一套写死的 11 槽位」，不是可检索、可按渠道组合的 skill 库。

---

### 层 4 · 场景 / 动作 / 情绪资产库

**已有：** 没有独立库。三类信息全部糅在 `looks[].text` 和 `modelSlots[].framing` 的自由文本里。

**后果：** 不能检索、不能交叉组合。扩品类 = 整包复制模板再手改。

---

### 层 5 · 生产引擎

**已有 —— 分层与那份方案画的一致：**

```
前端任务卡 → Next 后端 → job 队列 → 网关 → GPU / 生图 API → 拼版渲染 → 发布共享盘
```

而且业务逻辑写在 TS 里（`product-pipeline.ts` 编排、`product-layouts.ts` 排版），没有硬编码进 ComfyUI 节点 —— 恰好是那份方案明确建议的做法（它警告过「节点不稳定」会成为长期问题）。

**差别：** 商品套图这条线目前不走 ComfyUI，走网关调 gpt-image-2。ComfyUI（`src/lib/mono/comfyui.ts` + `config/comfyui-workflows/`）在仓库里是另一条线。

---

### 层 6 · 质检与数据闭环

**已有 —— 只有一半：**

- 尺寸校验 `verifyDetailOutputs`
- 颜色出现率启发式：生成图里应含有商品颜色的一块有意义区域，否则大概率是换了件商品。阈值 `COLOR_PRESENCE_DELTA_E = 20` / `COLOR_PRESENCE_MIN_RATIO = 0.02`。**只记 warning 不拦**（无人值守流程不能被误判卡住）

**缺口：**

- 视觉质检：人脸一致性、手指异常、logo 正确性、版型偏差、背景穿帮 —— 全无
- 商业闭环：点击率、转化率、**退货率**、素材生命周期 —— 全无

---

## 2. 两个方向上我们更靠前

那份方案的 14 步流程里，第 7 步（批量生成）之后基本一句话带过。我们真正落地了它没写的一段：

1. **成品形态是详情页，不是散图。** 固定 11 槽位版式（7 张模特图 + 2 张固定页 + 平铺页 + 细节页），产出可直接上架的一整套。
2. **工程细节。** 网络盘目录约定、主图复用跳过抠图、部分失败仍发布已完成槽位、按槽位可见的花钱模型、只重跑失败槽位。这些它只用「任务队列 / 失败重试」一行代过。

---

## 3. 最该注意的差异：品类

那份方案通篇按**女装**写，我们做的是**帽子**。差别比看上去大：

帽子是配饰，不涉及穿着，没有袖长、扣子数量、印花位置、版型垂感这些问题。它说的「比脸像不像更难」的那一整类风险，我们现在根本没碰到。

**如果要做女装，层 1 需要推倒重做**（分割 + 虚拟试衣 + ControlNet），现在这套「商品参考图 + 提示词」的路子撑不住。

---

## 4. 若要往那个方向走：最小增量三步

按「收益 / 改动成本」排序：

1. **固定模特身份**（收益最大，与现有架构最兼容）
   不必先训 LoRA。先在 `looks` 里挂人脸参考图，试 gpt-image-2 的多图参考能不能稳住身份。稳不住再考虑 LoRA。

2. **把资产从提示词里抽出来**（纯重构，不花生图钱）
   场景 / 动作 / 情绪从 `looks[].text`、`modelSlots[].framing` 的长句里拆成结构化字段。这一步决定了后面能不能「按渠道自动组合」，也是扩品类的前提。

3. **质检补人脸一致性**
   `measureColorPresence` 已经是这个位置的现成钩子，加一个同类判据即可，不用新起一套。

至于那份方案的「第三阶段 Agent 调度」—— 商品套图改造 plan 里的 M4（新增 `mono_product_pipeline` 工具）本来就在做，方向一致，不需要额外规划。
